# Project Directory Structure Plan

Updated: 2026-07-22

## Current Principle

This project now contains three different kinds of things:

1. paper/source-specific multiplier models, such as TCASI24 LSAM1/CSAM2;
2. group-provided FPGA multiplier RTL candidates;
3. experiment glue code, reports, LUTs, and learning notes.

The directory structure should make these boundaries visible. A good rule is:

```text
source-specific code stays source-specific;
shared experiment logic goes into neutral shared modules;
raw/provided RTL is kept separate from our generated reports and scripts.
```

## Recommended Top-Level Layout

```text
LLM-FPGA/
  am_lut_tcasi24/          # TCASI24-specific Python behavior model
  multiplier_models/       # Shared Python behavior helpers across multiplier sources
  FPGA_multiplier/         # Group-provided Verilog candidates and related RTL
  scripts/                 # Reproducible experiment entry points
  tests/                   # Smoke/exhaustive consistency checks
  outputs/                 # Generated LUTs, reports, figures
  docs/                    # Stable project docs and migration records
  study/                   # Learning notes, project notes, planning docs
  work/                    # External papers, copied open-source repos, rough work materials
```

## Directory Responsibilities

| Directory | Should contain | Should not contain |
|---|---|---|
| `am_lut_tcasi24/` | TCASI24 LSAM1/CSAM2 model, TCASI24-specific LUT generation helpers | Group FPGA candidate logic, AxCore-specific code |
| `multiplier_models/` | Generic LUT, signed-wrapper, metric helpers usable by multiple multiplier families | Paper-specific assumptions unless clearly named |
| `FPGA_multiplier/` | Teammate-provided accurate/approx Verilog, signed wrapper RTL related to those cores | Python experiment scripts or generated `.npy` outputs |
| `scripts/` | Commands that reproduce LUT generation, reports, RTL checks | Long notes or one-off manual scratch code |
| `tests/` | Minimal checks that catch wrong behavior quickly | Large generated data |
| `outputs/` | `.npy`, `.json`, `.md` reports, rendered figures | Source code needed to reproduce results |
| `study/` | Research notes, explanations, meeting/task plans | Generated LUT arrays |
| `work/` | External repos, PDFs, excerpts, temporary copied references | Core project modules |

## Why `signed_wrapper.py` Should Not Live Under `am_lut_tcasi24`

`am_lut_tcasi24` means: "models from the TCASI24 AM-LUT paper."

But the signed wrapper is a general experiment baseline:

```text
any unsigned 8x8 core -> signed int8 behavior baseline
```

It can wrap TCASI24, the group FPGA candidate, or another unsigned multiplier later. So it belongs in:

```text
multiplier_models/signed_wrapper.py
```

This keeps the naming honest and prevents a future reader from thinking the group FPGA candidate came from TCASI24.

## Near-Term Cleanup Plan

Already done:

```text
am_lut_tcasi24/signed_wrapper.py
  -> multiplier_models/signed_wrapper.py
```

Recommended next small cleanups:

1. Split generated LUTs by source:

```text
outputs/luts/tcasi24/
outputs/luts/fpga_signed_wrapper/
```

Current `outputs/fpga_luts/` is usable, but the above naming will scale better.

2. Rename broad report scripts later:

```text
scripts/run_error_report.py
  -> scripts/run_tcasi24_error_report.py
```

This avoids confusing TCASI24 reports with FPGA candidate reports.

3. Keep `FPGA_multiplier/approx_unsigned8x8/` as raw candidate source.

Do not edit candidate Verilog in place unless we intentionally create a modified design. Put our wrappers in a separate folder, currently:

```text
FPGA_multiplier/signed_wrapper/
```

If the RTL side grows, we can later move our authored RTL to:

```text
rtl/signed_wrapper/
rtl/testbenches/
```

For now, keeping wrapper RTL beside `FPGA_multiplier` is acceptable because it directly instantiates `approx88_cascade`.

## Practical Rule For Future Files

When adding a file, ask:

1. Is it a reusable Python behavior/metric helper?
   - Put it in `multiplier_models/`.
2. Is it specific to TCASI24?
   - Put it in `am_lut_tcasi24/`.
3. Is it group-provided or multiplier RTL?
   - Put it in `FPGA_multiplier/` or later `rtl/`.
4. Is it a command I run to reproduce an experiment?
   - Put it in `scripts/`.
5. Is it generated by a command?
   - Put it in `outputs/`.
6. Is it an explanation or planning note?
   - Put it in `study/` or `docs/`.
